# Refresh the harness of a seeded project

Brings the harness files to the current templates. Replaces only files proven unmodified, adds missing ones, never deletes, and writes the new version beside every locally edited file. A project with no `.claude/harness.json` goes through `general/implementation.md` instead.

**Proof.** A file counts as unmodified only when its sha256 is on the list `general/pristine-hashes.txt` for that path: the hash of a file a released plugin version shipped. The project's own records (`origin_hash` in `.claude/harness.json`, the `.claude/.harness-base/` copy) are not proof, because a refresh, a regen or a hand edit can rewrite them from the current bytes. The list is built by `general/gen-pristine-hashes.sh` (maintainer tool) from the released tags, so it is regenerated after each release tag exists; a file that carries a `__TC_` placeholder is never on it. Every other changed file is MODIFIED and gets a `<path>.templatecentral-new` file; the project file stays as it is. A project seeded by an older plugin version than the list covers (before 7.0.0), seeded from an unreleased build, or altered by a format pass gets a `.templatecentral-new` file for every changed file: that is the safe outcome, not an error. A missing list makes everything MODIFIED. A file with a `__TC_` placeholder (`docs/CONSTITUTION.md`) is always MODIFIED: the project's text differs from the template by design. The list covers every release tag that has a template tree (7.0.0 and later); earlier releases wrote the harness from guide text, so their files cannot be proven and get a `.templatecentral-new` file.

**Pending merges.** A second `--apply` never overwrites an existing `.templatecentral-new`. An identical one is reported as "pending merge"; a different one is reported as kept, with the instruction to merge or remove it. Exit is 1 while any merge is pending. The script prints "version not bumped: N file(s) wait for merge" and leaves `templatecentral_version` in `.claude/harness.json` as it is. It never edits `AGENTS.md`: the line-1 marker and the version line belong to the user, who updates them after the last merge. If `.claude/settings.json` waits while new hooks or `verify-harness.sh` were written, the script prints a WAITING FOR MERGE block: `verify-harness.sh` and `harness-live.sh` fail until the settings merge is done (for example `DENY RULE MISSING`), and the next step is the merge, then `bash .claude/verify-harness.sh`.

**Expect failures after a refresh.** A refreshed project is expected to fail the new content gates at first: `check-docs.sh`, `check-env-example.sh`, `check-supply-chain.sh`, `check-workflows.sh`, `check-dockerfile.sh`. They check the project's own README, `.env.example`, lockfile and registry settings, workflows and Dockerfile, which a refresh does not rewrite. Fix in this order: merge the `.templatecentral-new` files (`.claude/settings.json` first, then `verify-harness.sh` passes), then `.env.example` and docs (`check-env-example.sh`, `check-docs.sh`), then supply-chain settings (`check-supply-chain.sh`), then workflows and the Dockerfile (`check-workflows.sh`, `check-dockerfile.sh`). Run each failing script by hand and read its first lines. A refresh does not install git hooks: run the install step for the project's hook manager (for lefthook, install lefthook first, then `lefthook install`).

**Safety.** `--apply` checks every path it will write first (targets, sidecars, base copies, `.claude/harness.json`). A symlink, a path outside the project, or a symlinked `.claude/.harness-base` or `harness.json` makes it refuse with exit 2 before any write. A `<path>.templatecentral-new` that already exists is never overwritten: merge or remove it first. Any FAILED line ends with one `PARTIAL:` line listing what was written and what was not.

**Notes.** `--stack <nestjs|nextjs|vite-react|fastapi>` picks the stack when detection is ambiguous or finds none. A dry run exits 0 when only REPLACE or ADD are pending. A replaced file gets the template's file mode. The refresh never edits `.gitignore`: when it adds the review gate and `.gitignore` lacks `.claude/review/`, the plan names that line for you to add.

1. Dry run. It writes nothing and prints one line per file:
   ```bash
   bash "<skill-dir>/general/harness-refresh.sh" <project-dir>
   ```
   Show the plan. Classes: SAME, REPLACE, MODIFIED, ADD, GONE (recorded as seeded, no longer in the templates; report only).
2. Ask the user to confirm, in one message:
   - the git tree is clean (commit first), so the refresh is one diff;
   - the REPLACE and ADD lists;
   - each MODIFIED file gets `<path>.templatecentral-new` and stays as it is;
   - whether to run the baseline compare around the refresh. It runs the project's lint, typecheck and tests and installs pinned scratch tools (network).
3. Apply. Create `<scratch>` outside the project first when the user said yes to the baseline:
   ```bash
   bash "<skill-dir>/general/harness-refresh.sh" <project-dir> --apply --baseline <scratch>
   ```
   Without the baseline, drop `--baseline <scratch>`. The script refreshes `.claude/harness.json` and the base copies for the files it wrote, then runs `harness-live.sh`. Exit 1 means a file needs the user, a check failed, or the compare found a worse number or a changed gate configuration. For the compare, follow Phase 3 A step 5 of `general/implementation.md`: show the rows, never accept a worse number by editing a threshold, a suppression or an exclusion.
   An adopted project with many old lint, type or script findings: add `--gate-baseline` (or a bare `--baseline` as the last argument) to `--apply` to record them in `.claude/gate-baseline.txt` and copy `scripts/gate-baseline.sh`. Gates then fail only on findings not in that file, and the file may only shrink. A dry run with the flag runs the project's tools and prints what would be recorded; it does not write the baseline file. The file starts with a `v2` header, then one `# gate` line per gate that ran (even with zero findings), then the entries. A gate that stops applying or switches tool fails the check, and removing a gate line counts as growth. A file from an older format fails the checks; `--apply --gate-baseline` replaces it with a v2 file and prints a NOTE. A check script that prints nothing at exit code 0 did not run and fails; a lint or type tool that exits non-zero with no readable finding fails, and its stderr is shown only then. `gate-baseline.sh validate` checks the file's format only; `gate-baseline.sh growth <base-ref>` is the check for added entries and raised counts. Later, `--apply --gate-baseline --prune` drops entries that no longer match. In a project that has the gate ratchet, CI refuses growth of the file and any edit of `scripts/gate-baseline.sh`, judged with the merge-base copy. Covers lint, type check, `check-workflows.sh` and `check-dockerfile.sh`; coverage and policy gates stay absolute.
4. For each `.templatecentral-new` file, merge it into the user's file with the user, then delete the `.templatecentral-new` file. For `.claude/settings.json` merge structurally, never as text. Run `bash .claude/verify-harness.sh` once merged.
5. Show `git diff`; the user commits. GONE files stay until the user chooses to remove them.

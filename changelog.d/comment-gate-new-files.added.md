- Seeded comment gate for project source, built as new files and not registered anywhere yet: `skills/scaffold/shared/template/scripts/check-comments.sh` (readers `check-comments.mjs` for TypeScript and JavaScript, `check-comments.py` for Python). It judges only lines added or changed since the base ref (`--all` treats every line of the listed paths as new) and reports `file:line: comments/<rule>: problem. Fix: ...`. Rules: no trailing comment, no comment inside a function body or anywhere but the top of the file or directly above a declaration, at most 3 lines per block (one constant, `MAX_COMMENT_LINES`), no parenthetical aside, no comment wholly in brackets; over the limit, a project with `docs/adr/` or `docs/decisions/` is told to cite the ADR by number. Shebangs, licence headers and tool directives (`eslint-*`, `@ts-*`, `noqa`, `type: ignore`, `pragma`, `istanbul`/`c8`/`v8`, `NOSONAR`) are never judged. Comments come from the project's own `typescript` package (parser plus compiler scanner) and Python `tokenize`/`ast`, so markers in strings, template literals, regex and JSX text are not comments; a missing `node`, `python3` or `typescript` exits 2 with the fix. The base ref is the argument, else `BASE_REF`, else the merge base with the default branch; in CI an environment `BASE_REF` is accepted only when it names the pipeline target branch variable, and the report states how the base was chosen. Generated and vendored paths are skipped from one list. `scripts/seeded-comments.test.sh` covers each rule with a failing fixture and a clean control in both languages, diff scope, the ADR message, the missing-runtime exits and the CI refusal; it needs a `typescript` package (`TC_TEST_TYPESCRIPT_DIR` or a global install).
